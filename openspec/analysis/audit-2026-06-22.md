## 2. 部分完成功能（与 spec 存在偏差）

### 2.1 codegen —— `@Async` 自调失效（最严重）
**位置**：`ProjectJobServiceImpl.java:99,109-112`

```java
public ProjectJob execute(String projectCode) {
    // ... 创建 job
    this.generateCode(projectCode, projectJob);   // ← this. 调用，绕过 Spring 代理
    return projectJob;
}

@Async
public void generateCode(String projectCode, ProjectJob projectJob) {
    generateSV.aiCode(projectCode, projectJob);   // ← 实际同步执行
}
```

**Spec**：`GET /project/job/execute` 立即返回任务对象，**实际**：HTTP 线程被同步阻塞完整七步（git clone + 文件 IO + ZIP 打包可达分钟级）。`@Async` 注解完全失效。

**根因**：`this.generateCode(...)` 内部调用，Spring AOP 代理不会拦截。

### 2.2 codegen —— `ProjectJob.code` 关系违反约定
**位置**：`ProjectJobServiceImpl.java:90-91`

```java
projectJob.setId(uidGenerator.getUID());    // id = UID-A
projectJob.setCode(String.valueOf(uidGenerator.getUID()));  // code = UID-B（独立 UID）
```

**Spec**：`code = String(id)`。`execute` 之后用 `code` 查 `ProjectJob`，但 `id != code`，多处 `update(...eq(Code...))` 与"按 id 查"行为漂移。`ProjectJobServiceImpl.save`（line 50）也独立发 UID 当 code，与 `Project` 的 `code=String(id)` 约定不一致。

### 2.3 sql-parse —— `parse()` 清场 SQL 字段错用
**位置**：`ProjectServiceImpl.java:320-325`

```java
for (ProjectMap projectMap : projectMapList) {
    mapClassTableMapper.delete(...eq(MapClassTable::getCode, projectMap.getMapClassTableCode()));  // ✓
    mapFieldColumnMapper.delete(...eq(MapFieldColumn::getCode, projectMap.getMapClassTableCode()));  // ✗
    //              字段应是 ::getMapClassTableCode
    mapRelationshipMapper.delete(...eq(MapRelationship::getCode, projectMap.getMapClassTableCode()));  // ✗ 同样错
}
```

**结果**：重 init 时只删 `MapClassTable`，**`MapFieldColumn` 和 `MapRelationship` 残留**，`isParseTable=Y` 之后表格与字段对不上，生成代码时出现孤儿字段与僵尸关系。

### 2.4 sql-parse —— `createDatabase` 幂等性破坏
**位置**：`ProjectServiceImpl.java:284-300`

```java
long i = databaseDAO.count(database);
if (i <= 0) {
    // ... 建库并 return true
}
return false;  // ← 库已存在时静默 false
```

`execute(code)`：`if (flag) parse(code); if (!parse) throw Server_Error;`

**结果**：已 init 过的项目二次 init → `createDatabase` 返回 false → `parse` 不跑 → `execute` 不报错 → HTTP 返回 200 + 客户端以为成功。**静默成功**，违反 spec "idempotent" 与 `init` 重新生成映射的语义。

### 2.5 project —— `delete()` 路径前缀错用
**位置**：`ProjectServiceImpl.java:214, 223`

```java
String projectPath = new HandleFuncs().getCurrentClassPath() + settingWorkspace.getV() + "/" + project.getEnglishName();
```

`getCurrentClassPath()` 返回 **classpath**（`classes/` 目录），不是工作空间根。`settingWorkspace.getV()` 已经是绝对路径（如 `/tmp/aicode/workspace`）。拼接后变成 `/.../classes/tmp/aicode/workspace/<name>`，**永远不存在**，工作空间不会被删。`Repository_Path` 同样。

### 2.6 codegen —— 模板清理依赖 `gitHome` 拼写
**位置**：`GeneratorSVImpl.java:252-267` 与 `prepareframeworksTemplateList` 同源

```java
String project_template_Path = template_Path + frameworks.getGitHome()
        .substring(frameworks.getGitHome().lastIndexOf("/") + 1)
        .replace(".git", "");
```

`frameworks` 中 `gitHome` 实际存在拼写错误（`aicode-tamplate.git`、`aicode-template.git` —— AGENTS.md 标注"不要顺手改"），清理逻辑会得到 `aicode-tamplate` / `aicode-template` 子目录。但 **克隆时也用同样的 gitHome**，路径能对上。问题：清理的是「上次 clone 的目录」，不是「本次」；且如果同一框架被改过 gitHome，旧目录永远删不掉。

### 2.7 codegen —— 模板清理时机错
**位置**：`GeneratorSVImpl.java:193`（在第 4 步生成后调用 `cleanTemplates`）

`cleanTemplates` 在生成源**之后**才清空 `frameworks_template` 表与模板目录。但如果生成中失败（异常被 catch）`cleanTemplates` **不会执行**，下次构建看到的是上次的 `frameworks_template` 行 + 模板已删除的物理目录，导致全部模板路径 404。

应挪到 `finally` 块。

### 2.8 codegen —— 反向关联强制 OneToOne
**位置**：`MapRelationshipController.java:84-89`

```java
MapRelationship mapRelationshipFlag = this.load(associateCode, mapClassTableCode);
mapRelationshipFlag.setMainField(joinField);
mapRelationshipFlag.setJoinField(mainField);
mapRelationshipFlag.setIsOneToOne(YNEnum.Y.name());   // ← 强制
mapRelationshipFlag.setIsOneToMany(YNEnum.N.name());
```

**结果**：建立 `OneToMany`（A→B）时，反向自动建的关系是 `OneToOne`，与原关系方向不一致。spec 未明确，但语义上反向应该保持 OneToMany（N→1 = OneToOne 反向），代码逻辑反了。

### 2.9 codegen —— `e.printStackTrace()` 残留
**位置**：`GeneratorSVImpl.java:230, 360, 568, 569, 612, 654, 686`；`ProjectJobController.java:176`；`LogsSVImpl.java:127, 185, 187, 191`；`ProjectJobServiceImpl` 通过 `execute` 异常路径。

违反 `code-style.md §11`：禁止 `e.printStackTrace()` 作为唯一处理。应统一为 `log.error("上下文", e)`。

### 2.10 codegen —— `e.getMessage()` 推送 WebSocket
**位置**：`GeneratorSVImpl.java:232, 569`；`LogsSVImpl.java:127`

把异常 message 直接推到前端 WebSocket / 写入日志。`getMessage()` 可能包含文件路径、SQL 片段、类名等内部信息，对前端不安全；日志落盘时也不利于结构化查询。

### 2.11 project —— `delete` 物理删除与 `state=Delete` 不一致
**位置**：`ProjectServiceImpl.java:167-169`

```java
project.setState(ProjectState.Delete.name());
projectMapper.delete(new LambdaQueryWrapper<Project>().eq(Project::getCode, project.getCode()));
```

先设 state=Delete 又物理删除，state 字段无意义；spec 中 `state: Enable/Disenable/Delete` 三态实际只有物理存在与否。

### 2.12 project —— `list` 无 token 返回空
**位置**：`ProjectController.java:285-302`

```java
if (StringUtils.isBlank(token) || "null".equals(token)) {
    return R.success(pageVO);  // 返回空 Page
}
```

token 缺失返回空列表而不是 401/未授权。前端可能误判为"无项目"。

### 2.13 settings-repository —— `modify` 按 code load 但可能覆盖他人
**位置**：`ProjectRepositoryAccountController.java:131-140`

```java
ProjectRepositoryAccount load = ...getOne(eq(Code, projectRepositoryAccount.getCode()));
if (load != null) {
    projectRepositoryAccount.setId(load.getId());
    projectRepositoryAccountService.updateById(projectRepositoryAccount);
}
```

`updateById` 用 entity.id，但**没校验 projectCode 归属**，A 项目的 modify 包可改 B 项目的记录（如果传 code 不带 projectCode 校验）。

## 4. 技术债务

### 4.1 控制器直调 `*ServiceImpl`（违反 facade 契约）
**位置**：16 个 Controller 全部 `import x.x.service.XxxServiceImpl;` 而非 `import x.x.service.XxxService;`（从 facade）。

按 `code-style.md §2 §4`：业务接口声明在 facade、实现放 aicode；Controller 跨域调用应走 facade 接口。但实测几乎所有 Controller 注入的是 `aicode.project.service.ProjectService`（**也是 Impl 子包**），不是 `facade.project.service.ProjectService`。

> 例外：`ProjectJobController` 注入 `ProjectJobService`（位于 `aicode.project.service`，是 ServiceImpl），但 `facade` 实际没有该接口。

实际上"facade 与 aicode 的 service 子包"在当前项目**结构并存但未对齐**：`facade.account.service.AccountService` 是接口（被 `AccountController` 通过 `aicode.account.service.AccountServiceImpl` 实现），但 `facade.project.service` 只放 `GenerateSV`、`LogsSV`、`ProjectSqlService` 等少量接口，**绝大多数 `*Service` 接口根本不在 facade**。

**债**：要么把缺位的 `*Service` 接口从 `aicode` 上提到 `facade`（工作量较大），要么改 spec 承认现状（文档改动小）。建议前者但需要业务理解。

### 4.2 `GeneratorSVImpl` 742 行单体类
承载：workspace 创建、模板克隆、模板登记、引擎适配、路径解析、占位符替换、文件渲染、状态枚举衍生、SQL 发射、Git 推送、ZIP 打包。

应拆：`WorkspaceBuilder` / `TemplateDownloader` / `TemplateEngineAdapter` / `TargetPathResolver` / `SourceRenderer` / `SqlEmitter` / `GitCommitter` / `ZipPackager`。

### 4.3 16 个 Controller，11 个含 @Deprecated 端点
未实际删除（只加 `@Deprecated` 注解 + Javadoc）。`/project/sql/list`、`/project/sql/delete`、`/project/job/build` 等还活着但前端不用。建议二次扫描后再统一清理。

### 4.4 路径处理散落 `convertPath` 字符串 replace
`GeneratorSVImpl.convertPath` 5 次 `.replace("//", "/")`，调用方仍可能拼出多 `/`、`\`。建议抽 `PathService` 统一规范化。

### 4.5 `MybatisPlusConfig` 旧配置文件未挂载
`aicode/src/main/java/com/aicode/config/MybatisPlusConfig.java` 存在但被 `MybatisPlusConfigTidb` / `MybatisPlusConfigUid` 取代，前者已无 @Configuration 注解，可删除。

### 4.6 `LOG_HOME` 未在 `logback-info.xml` 启用
`logback-info.xml:3` `property name="LOG_HOME" 注释掉`。`db/data.sql` 不影响，但 `LogsSVImpl` 写入的日志文件路径（`workspace/<accountName>_<englishName>_logs/<datetime>.log`）**只**靠 `Setting.Workspace` 解析，与 `LOG_HOME` 无一致性保证。

### 4.7 静态 `WSClientManager` 持有 Session
`ConcurrentHashMap<String, Session>` 静态内存不清理断开连接；多实例部署时跨节点日志推不到。前端重连后无 sessionId 重放能力。

### 4.8 Build 任务缺幂等 / 防重入
`execute(code)` 无锁。同一项目并发 `execute` 两次会创建两条 `ProjectJob` 互踩工作空间与 ZIP。

### 4.9 `e.printStackTrace()` 多处
（详见 §2.9）

### 4.10 字段类型 `classModel` 行为
`MapClassTable.classModel` 字段在 `parse()` 流程中**未被设置**（`MapClassTable.toJava()` 不填它），但 `generator` line 473、498 用 `mapClassTableObj.getClassModel()` 分组，导致 `models` 全为 `null`、`modelDatas` 全空、生成的代码无 module 维度。**结构性 bug**。

## 5. 风险项（按影响 × 概率排序）

| ID | 等级 | 风险 | 触发条件 | 影响 |
|----|------|------|----------|------|
| R1 | **高** | `@Async` 自调失效（§2.1） | 每次 `execute` | HTTP 线程同步阻塞 30s~min，前端超时、虚拟线程未用上 |
| R2 | **高** | `parse` 清场字段错用（§2.3） | 项目重 init | 映射表残留，生成代码含孤儿字段/关系 |
| R3 | **高** | `delete` 路径前缀错用（§2.5） | 每次 `delete` | 工作空间与 ZIP 不被删除，磁盘泄漏 |
| R4 | **高** | `createDatabase` 静默成功（§2.4） | 二次 init | 客户端误以为成功但什么都没做 |
| R5 | **高** | `classModel` 永远 null（§4.10） | 每次 `generator` | `modelClasses/modelDatas` 空，模块维度不参与生成 |
| R6 | **中** | 模板清理失败 / 时机错（§2.6, §2.7） | 构建失败 / 异常 | 旧模板遗留在 `Template_Path`，下次构建看到空目录 |
| R7 | **中** | 反向关联强制 OneToOne（§2.8） | 建立关系 | OneToMany 关系方向错乱 |
| R8 | **中** | 无鉴权（§3.6, §3.7） | 任何访问 | 项目/SQL/凭据全裸露 |
| R9 | **中** | 凭据明文（§3.8） | 数据库泄露 | 模板仓库/产物仓库密码泄漏 |
| R10 | **中** | 异常 message 直推前端（§2.10） | 构建失败 | 内部路径/SQL 暴露到前端日志 |
| R11 | **中** | `isIncrement=Y` 无效（§3.4） | 选增量模式 | 仍按全量生成，与用户预期不符 |
| R12 | **中** | 并发 build 缺锁（§4.8） | 同一项目双击 | 工作空间互踩、ZIP 写入冲突 |
| R13 | **中** | `e.printStackTrace()` 残留 | 任何异常 | 日志格式不一致，缺失堆栈上下文 |
| R14 | **低** | `code ≠ String(id)`（§2.2） | 查询任务 | 按 code 查与按 id 查的语义漂移 |
| R15 | **低** | `list` 缺 token 返回空 | 无 token 访问 | 前端误判空数据 |
| R16 | **低** | RepositoryAccount 改覆盖风险（§2.13） | 跨项目 modify | 越权修改他人凭据 |
| R17 | **低** | SVN 静默假成功（§3.2） | type=SVN | 配置 SVN 的项目无产物 |
| R18 | **低** | `delete` state 字段无意义 | 任何分析查询 | 误导后续审计 |
| R19 | **低** | @Deprecated 端点不删 | 时间累积 | 路由膨胀、误用 |
| R20 | **低** | `MybatisPlusConfig` 死文件 | 误读代码 | 新人困惑 |
